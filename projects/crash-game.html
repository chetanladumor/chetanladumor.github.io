Provably Fair Multiplayer Crash Game Engine

A high-frequency real-time betting platform capable of processing thousands of simultaneous bets per round, powered by SHA-256 cryptographic provably fair verification, 50ms state broadcasting, and sub-millisecond atomic cashouts.

1. Executive Summary & System Challenges

Multiplayer Crash is an intensive real-time iGaming format where a multiplier curve ascends dynamically from 1.00x upwards. Players place bets during a pre-round countdown and attempt to cash out before the rocket crashes at an unpredictable threshold.

From a systems engineering standpoint, Crash presents two non-negotiable architectural requirements:

  • Cryptographic Provable Fairness: Guaranteeing to players and regulators that the crash point is predetermined before bets open and cannot be manipulated based on total wagering volume.
  • Sub-Millisecond Concurrency & Race Condition Prevention: Handling hundreds of cashout requests arriving in the exact same millisecond immediately prior to a crash, guaranteeing atomic balance crediting without double-spends.

2. Cryptographic Fairness & Verification Architecture

Fairness is guaranteed through a public commitment scheme combining three cryptographically isolated seeds:

  • Server Seed Pre-Commitment: A 256-bit cryptographically secure seed is generated on the server using the Fortuna PRNG algorithm. Its SHA-256 hash is published to all connected clients before wagering opens. Because the hash is public, the server cannot alter the outcome mid-round.
  • Client Seed Entropy Injection: A public seed provided by players or derived from external public block headers. This guarantees the operator could not have pre-calculated a seed favorable solely to the house.
  • Sequential Nonce Tracking: A strictly incrementing counter tracking total lifetime rounds for complete audit trail linkage.
  • Post-Round Verification: The instant a round crashes, the unhashed Server Seed is revealed. Clients can locally reproduce the cryptographic hash and confirm that the outcome matched the pre-committed hash.

3. Real-Time Round Lifecycle & State Machine

The game loop executes via an in-memory high-precision timer decoupled from database I/O, guaranteeing zero latency jitter across thousands of concurrent players:

Phase 01

Wagering Window & Cryptographic Commitment

6-Second Fixed Countdown
🎯 Client Inbound

Players submit bet amounts via WebSocket; payload is sanitized using Joi schema validation.

⚙️ Engine Concurrency

Balances are reserved atomically in Redis (DECRBY) to prevent negative balance race conditions.

🔒 Cryptographic Proof

Server computes SHA-256 of Server Seed and broadcasts the hashed commitment to all players before bets close.

↓
Phase 02

Active Flight & Multiplier Tick Loop

50ms High-Frequency Ticks
⚡ Real-Time Broadcasting

Node.js server clock drives 50ms tick intervals, broadcasting current multiplier and live player counts via Socket.IO.

📡 State Fan-Out

Redis Pub/Sub adapter replicates tick events across multi-core Node.js cluster processes with under 15ms latency.

🛡️ Threshold Guard

Active flight continuously checks if elapsed time has crossed the predetermined deterministic crash point.

↓
Phase 03

Sub-Millisecond Atomic Cashout Ingress

< 1ms Processing SLA
⚡ Atomic Execution

Cashout claims execute inside a single Redis Lua script, validating round active status and multiplier bounds atomically.

💰 Financial Settlement

Calculates winnings (Bet × Current Multiplier) and credits player balance in memory with zero race hazard.

📢 Instant Feedback

Pushes cashout acknowledgment to the player and broadcasts the win event to the global table leaderboard.

↓
Phase 04

Crash Resolution, Seed Reveal & Audit

3-Second Settlement & Cooldown
💥 State Transition

The instant crash point is reached, state flag transitions to CRASHED; all pending un-cashed bets are marked as bust.

🔍 Verifiability

The unhashed Server Seed is revealed in the payload, allowing any player to locally verify cryptographic fairness.

💾 Persistence Layer

Asynchronously persists round statistics, bets, and ledger balances to MongoDB, then triggers the next round cycle.

4. Concurrency Engineering: Atomic Redis Lua Scripts

⚡ Preventing Concurrency Race Conditions

If a player clicks cashout at 1.99x while the server calculates a crash at 2.00x, network packets arrive simultaneously. Traditional multi-query database transactions introduce lock contention and race conditions. By executing the cashout check, state validation, and balance crediting inside a single Redis Lua script, the operation is completely serialized and atomic. Either the cashout is recorded strictly prior to the crash flag, or it is rejected cleanly—guaranteeing zero financial discrepancies.
