Spillorama Multi-Game Bingo Infrastructure (Norway)

Designed and built the hybrid distributed gaming backend synchronizing 40+ physical bingo halls in Norway with thousands of concurrent online players, achieving sub-100ms state consistency between overhead TV hall displays and player touchscreens.

1. Project Overview & Challenge

In Norway, Bingo is a widely popular social entertainment pastime with dozens of licensed physical halls operating simultaneously. Spillorama modernized this infrastructure by unifying 40+ physical bingo venues with web and mobile players into one synchronized national network operating live at https://spillorama.no/.

The core engineering challenge was strict real-time clock and state synchronization:

  • When a bingo ball is drawn by the server, players watching the large overhead TV screens in Oslo or Bergen must see the ball at the exact same millisecond as players dabbing cards on their mobile devices at home.
  • Any clock drift, out-of-order event delivery, or delayed draw packet would compromise game fairness and violate Norwegian gaming regulations.
  • The system powers five completely distinct game modes running round-the-clock with automated scheduling and zero server restarts.

2. The Five Synchronized Game Engines

The platform encapsulates five custom game variants:

  • Papir Bingo (Hybrid 75-Ball): Synchronizes traditional paper cards sold in physical halls with digital tickets, tracking multi-tier line wins (1-line, 2-line, Full House).
  • Lyn Bingo (Rapid 21-Ball): Fast-paced 21-ball speed bingo with 3-second draw tick cycles and rapid settlement.
  • Bingo Bonanza: Configurable geometric win patterns, dynamic ticket pricing, and progressive multi-hall jackpot pooling.
  • Turbo Mania (33-Ball): High-energy format with randomized multiplier balls that scale cash payouts upon pattern completion.
  • SpinnGo: A hybrid game model combining multi-ticket bingo rounds with secondary bonus rounds (Wheel of Fortune and roulette wheel triggers).

3. Distributed Real-Time Synchronization Pipeline

To prevent clock drift and maintain sub-100ms synchronization across 40+ physical bingo venues and mobile players, the draw lifecycle operates across four distributed stages:

Stage 02

Central BullMQ Scheduler & Redlock Mutex

15-Second Automated Interval
⏱️ Centralized Clock

Internal Node.js timers are replaced with Redis Sorted Sets (ZSET) and BullMQ job queues, eliminating server clock drift.

🔒 Redlock Mutex Guard

Cluster workers compete for a Redis distributed lock (SETNX with Lua lease). Only the lock-winning worker triggers the draw, preventing duplicate ball generations.

Stage 03

Cryptographic Ball Draw & Binary Fan-Out

< 100ms TV & Mobile Alignment
🎲 Fortuna PRNG

Draws candidate balls from the physical pool (75-ball, 21-ball, or 33-ball) using cryptographically secure Fortuna pseudo-random algorithms.

📡 Redis Adapter Broadcast

Fires binary-serialized draw events via @socket.io/redis-adapter across multi-node servers, rendering simultaneously on hall TVs and mobile phones.

↓
Stage 04

In-Memory Bitmask Evaluation & bulkWrite Settlement

Sub-Second Ticket Reconciliation
⚡ Card Bitmask Checks

Node.js workers evaluate tens of thousands of active tickets against winning patterns (1-line, 2-line, Full House) using fast bitwise operations in memory.

💾 MongoDB bulkWrite

Winner tickets and jackpot allocations are flushed in batched bulkWrite operations, notifying third-party providers (Metronia & Ok Bingo) for fiscal compliance.

4. Key Architectural Decisions & Gotchas Solved

1

Eliminating In-Memory Timers (setTimeout / setInterval)

In a multi-node cluster, using native setInterval for ball draws causes clock drift and duplicate ball draws if multiple servers trigger ticks. All internal timers were replaced with Redis Sorted Sets (ZSET) and BullMQ delayed job queues. The draw clock is centralized in Redis, ensuring atomic, monotonic ball draws.

2

Preventing Split-Brain Duplicate Draws (Redlock Pattern)

When a draw tick fires, multiple cluster workers could attempt to resolve the draw simultaneously. Using Redis distributed locks (`SETNX` with Lua script expiration), only one worker node can acquire the draw lock. If that node crashes mid-draw, the lock safely releases and another node resumes state seamlessly.

3

Sub-100ms TV Display & Player Alignment

TV display screens in physical venues run WebGL display clients connected over persistent WebSockets. By using the Socket.IO Redis adapter with binary message serialization and pre-fetching next-ball animations, the visual draw renders simultaneously on hall screens and handheld phones with under 100ms variance.

4

High-Write Ticket Validation via bulkWrite

With tens of thousands of active tickets per round, evaluating every card sequentially in MongoDB would cause disk I/O starvation. In-memory card bitmask evaluation was implemented on Node.js workers and flushed prize winners in batches using MongoDB bulkWrite with compound index lookups.
